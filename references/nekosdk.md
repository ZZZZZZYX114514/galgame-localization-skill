# NEKOPACK4A 与 NekoSDK ADVSCRIPT2

本参考描述随附脚本已经处理过的格式变体。新样本先比较文件头、索引边界与记录布局，再验证一个最小修改。

## 归档布局

所有整数均为 little-endian。

| 字段 | 含义 |
| --- | --- |
| 偏移 0，10 字节 | `NEKOPACK4A` |
| 偏移 10，u32 | 索引长度 |
| 偏移 14 起 | 索引记录与结束标记 |
| 每条记录 | u32 文件名字节数、文件名字节、u32 混淆偏移、u32 混淆大小 |
| 记录混淆键 | 文件名字节求和，包含原有 NUL 字节 |
| 实际偏移与大小 | 对应 u32 与混淆键异或 |
| 索引末尾 | 文件名长度为零的 u32，计入索引长度与数据起点 |

引擎查询可选 `.alp` 等缺失文件时可能扫描到零长度记录。因此结束标记和索引长度需要与运行时保持一致。自有工具能读回一个包，只能证明这些工具对这个包达成一致。

检查索引记录边界、数据起点、条目范围、名字顺序与原始字节。重打包时对每个未修改条目保留其原始压缩数据，用 `build_archive_packed` 仅重新排列索引和文件位置。打包全部解压内容的路径会重新压缩所有条目，适合获得完整资源操作授权后的场景。

## 条目压缩

每个条目的末尾四字节为解压后长度。前面是 zlib 数据，其头四字节经过异或。

```python
key = packed_size // 8 + 0x22
for index in range(4):
    header[index] ^= key & 0xFF
    key <<= 3
```

`encode_entry` 与 `decode_entry` 实现此布局。验证实际解压长度。原始条目包含该压缩层时，直接保留原始 blob 可避免改动无关资源。

`nekopack.py list` 仅解析索引。`extract`、`verify` 会解压资源内容，使用前按用户授权与图片限制确定范围。正文提取优先使用 `text_pipeline.py`，它按脚本扩展名与文件头选择内容。

## 对白记录

脚本头为 `NEKOSDK_ADVSCRIPT2`。当前实现识别 CP932 编码的 `[テキスト表示]` 和 `[ログ追加]`，每段从命令前的长度字段开始，包含长度前缀的人物名和正文。非零字符串长度计入末尾 NUL。其他命令及尾随数据保留原字节。

`text_pipeline.py extract` 导出 UTF-8 JSONL，字段如下。

| 字段 | 用途 |
| --- | --- |
| `entry`、`chunk`、`id` | 归档条目与当前格式的记录位置 |
| `source_sha256` | 原始脚本解压后的哈希，写回前检查版本 |
| `name`、`text` | CP932 原人物名与原文 |
| `translation_name` | 译名，`null` 时保留原人物名 |
| `translation` | 本批译文 |

`apply` 接收本次构建的全部已完成记录，检查重复位置、源哈希、目标 GBK 可编码性及选中条目的存在性，然后生成新归档。输出路径须独立且尚未存在。分批续译时将新记录合并到已完成表，再从同一 CP932 原版输入重建，以保留先前批次。

此导出表的位置依赖当前原脚本。原脚本发生变化时重新提取，并根据原文和上下文重新对齐译文。

## 编码与字体

随附写回器采用 CP932 读取原文、GBK 写入译文。使用前确认当前游戏的文本到宽字符转换和字体确实接收 GBK。中文显示需要脚本编码、解码调用和字体字符集同时匹配。`translation_name` 为 `null` 时原姓名字节会保留，按 GBK 解码的运行时需要同时检查姓名和其他残留 CP932 文本的显示。

若需要修改可执行文件，先识别实际对白与 UI 的解码调用点，在独立副本上做最小补丁，并比较调用点以外的字节。全局替换代码页常量会同时影响日文资源名、路径和配置读取，需要逐条调用链证据。

## 独立检查

使用手工字段检查或独立解析方式验证索引结束标记、偏移与大小，再执行原内容重打包测试和最小改文测试。引擎对齐规则、文件名字节和可选资源查找均可能影响启动。

压缩包回环测试、文件哈希和实际游戏启动分别记录结果。启动崩溃时按 [验证与交付](verification-and-delivery.md) 缩小变化范围。
